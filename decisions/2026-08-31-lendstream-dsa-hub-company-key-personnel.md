## Decision: An Applicant can now be a company; a company can have Key Personnel (directors/partners/authorized signatories), and each key person is a full, independent Applicant of their own — HubSpot Company/Contact style — so they get their own applications, list-page row, and detail page for free, distinct from the company's own applications.

## Context
User asked: an Applicant can be a company name, and if so, the list of key people under that company needs to be captured; clicking the applicant should show key personnel details and "the application under company or other products present under the key personnel." That last phrase — key personnel having their *own* products, separate from the company's — was the crux of the design question, so it was put to the user directly before building (two `AskUserQuestion` calls, since there was no single obvious default):

1. Should a key person be a lightweight contact record only, or a fully linked, independent Applicant profile that can carry its own applications? User chose the full-linked model, describing it as "built like a hubspot model" — i.e. Company/Contact are separate-but-associated first-class objects, same as HubSpot.
2. Should "mark as company" be decided at New Lead creation time, or after the fact on the Applicant page? User chose after-the-fact, explicitly to leave the New Lead modal (already pixel-matched to the prototype this same day) untouched.

## Alternatives considered
- **Key personnel as a plain contact list** (name/designation/PAN/mobile/email fields living directly on a `key_personnel` row, no linkage to `applicants`). Simpler, but doesn't satisfy "other products present under the key personnel" — there'd be nowhere for their personal applications to live or be discovered from the company's page. Rejected per the user's explicit choice.
- **A separate `companies` table**, distinct from `applicants`, with its own shape. Rejected — an Applicant already *is* "the person or entity a loan is being applied for/by"; a company is just an Applicant with `entity_type = 'COMPANY'`. Reusing the same table means every existing piece of Applicant machinery (RLS, the list page, the detail page, `createApplication`, the Dashboard preview) already works for companies and key personnel with zero changes.
- **Deciding company/individual at New Lead creation time** (a toggle on that modal). Rejected per the user's explicit choice — keeps that modal exactly matching the prototype, which has no such toggle.

## Reasoning
- `applicants.entity_type` (`'INDIVIDUAL' | 'COMPANY'`, default `'INDIVIDUAL'`) is the only schema change to the `applicants` table itself. `client_name` holds the company name when `entity_type = 'COMPANY'` — no separate `company_name` column, since it's the same "who this is" field either way.
- New `key_personnel` table is purely the association + role: `company_applicant_id`, `linked_applicant_id` (unique — one real person can't be key personnel at two companies at once), `designation`. No name/PAN/phone/email duplicated here — those live on `linked_applicant_id`'s own `applicants` row, so there's exactly one place each fact can go stale, not two.
- `addKeyPersonnel` (`app/actions/keyPersonnel.ts`) creates the key person as a brand-new individual Applicant, then links it — mirroring `createLead`'s own rollback-on-failure pattern (delete the just-created Applicant if the association insert fails, checking the row count rather than trusting the absence of `error`, per the standing RLS-row-count rule this project already follows).
- `markApplicantAsCompany` is a plain form action directly on the Applicant detail page (no client component needed) — one click, no separate route, reversible only by direct DB edit for now (no "unmark" UI, since a company that has already gained key personnel shouldn't quietly lose that context by accident).
- RLS on `key_personnel` mirrors every other table's "own rows, or ops sees all" pattern, scoped through the parent company's `agent_id` via an EXISTS join (same shape as `documents_select_via_lead` etc.) — insert is owner-only, no ops carve-out, matching `leads_insert_own`'s existing precedent that ops views everything but never originates data on a partner's book.
- The Applicant detail page gained: an entity-type badge, a "Mark as company" action (individual only, owner only), a "Key personnel" card (company only) listing each linked person with their own application count and a link into their own detail page, and a reverse link ("Director at {Company}") on a key person's own page pointing back to the company. All existing sections (Applicant identity, RM, Active/Closed applications) are unchanged and just as correct for a company as for a person.
- Fixed an adjacent bug surfaced while wiring this up: `NewApplicationModal`'s close button was hardcoded to `/partner`, which was fine when it was only reachable from the Dashboard but became visibly wrong now that it's also reachable from an Applicant's own detail page and the Applicants list. Added a `closeHref` prop, threaded from each caller.
- Verified live end-to-end with a temporary test company (never touched the real "Abhishek" applicant): marked it as a company, added a key person (full name/mobile/designation/PAN), confirmed they appear as their own row on the Applicants list with the "Company" badge correctly on the parent only, added an application under the key person specifically, and confirmed the company's own application count stayed at 0 while the key person's own count became 1 — exactly the "application under company OR other products present under the key personnel" distinction asked for. All test data removed afterward.

## Trade-offs accepted
- No "remove key personnel" UI yet (only add) — a mis-added association can currently only be undone by direct DB edit. Reasonable for a first pass; add if this comes up in practice.
- No search/autocomplete to link an *existing* Applicant as key personnel of a company (e.g. if that person already has their own individual Applicant record from an earlier, unrelated file) — `addKeyPersonnel` always creates a brand-new individual Applicant. If the same real person already exists as a standalone Applicant, adding them as key personnel today creates a second, separate record rather than merging. Not raised as a concern by the user; worth flagging if duplicate-person scenarios come up.
- A key person's own `entity_type` can itself be flipped to `'COMPANY'` later (nothing blocks it) — a real-world nested-ownership scenario (a director who runs their own separate business) is allowed, not specially handled or restricted.
