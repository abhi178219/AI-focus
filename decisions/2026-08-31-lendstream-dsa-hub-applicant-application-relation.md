## Decision: Added a real Applicant entity above `leads`, in a HubSpot Contact→Deals shape — one Applicant, many Applications (leads) underneath — surfaced as a new section on the Dashboard. "New lead" always creates a fresh Applicant + Application pair together; a second Application for an existing Applicant is only ever added explicitly from that Applicant's own row, never inferred by matching phone number.

## Context
User asked for a dashboard subsection "similar to HubSpot": an Applicant created via the existing New Lead form, with the loan Applications currently modeled as flat `leads` rows nested underneath it. Same request also asked for "New lead" to be re-checked against the original prototype (a separate, unrelated fidelity gap — see below) and for an "ops advisor" pass on the new relation before considering it done.

## Alternatives considered
- **Lightweight, schema-free grouping**: group existing `leads` rows by phone number purely for display, no new table. Rejected — the user's own wording ("an applicant... created using the current lead form, and under it the applications") describes a real creation event and a real containment, not a computed view; a display-only grouping wouldn't actually let a second real Application be filed under an existing Applicant.
- **Auto-match a new "New lead" submission to an existing Applicant by mobile number.** Asked the user directly (AskUserQuestion) rather than guessing — a shared family phone or a mistyped digit could silently merge or misfile two different real people, and there's no way to make that call safely without knowing how this DSA's customers actually behave. User chose explicit-only.
- **Full refactor of `leads`/UI to read identity fields (name/phone/email/address) through a join to `applicants`, dropping them from `leads`.** Rejected for this pass — much larger blast radius across every existing tab/component that already reads `lead.client_name`/`lead.phone`/etc. directly. Instead, `applicants` holds the canonical identity, and each `leads` row keeps its own denormalized snapshot of it at creation time (arguably correct anyway — a real loan application captures its own KYC snapshot even for a repeat customer). Applicant identity fields are the source of truth going forward for *new* Applications under an existing Applicant (via `createApplication`), but existing per-lead UI is untouched.

## Reasoning
- `createLead` (`app/actions/leads.ts`) now inserts into `applicants` first, then `leads` with `applicant_id` set, rolling back the just-created Applicant if the Application insert fails (no orphaned Applicant with zero Applications).
- New `createApplication(applicantId, formData)` action asks only for Product + Amount, copying identity fields from the named Applicant — reachable only via a "+ New application" link on that Applicant's own dashboard row (`/partner/applicants/[id]/application/new`), matching the "explicit only" choice.
- `applicants` table + RLS mirrors `leads`' own "own rows, or ops sees all" pattern exactly (`agent_id = auth.uid() or private.is_ops_admin()`).
- Backfill: every pre-existing lead already represented one applicant 1:1 under the old model, so each got a real `applicants` row built from that lead's own already-real data (name/phone/email/address) — no fabricated fields, `applicant_id` on `leads` is `not null` after backfill.
- Dashboard "Applicants" card groups the already-fetched `leads` rows by `applicant_id` client-side (one extra query for `applicants`, no N+1) and renders each Applicant with their Applications nested underneath, each linking through to the existing lead-detail page.

## Trade-offs accepted
- No "all applicants" page yet — the Dashboard card lists everyone with internal scroll past a certain count, matching the existing "Needs attention" panel's pattern. A dedicated `/partner/applicants` page is a reasonable next step if the list grows.
- Identity fields are denormalized onto each `leads` row rather than joined live from `applicants` everywhere — editing an Applicant's phone/email later (no edit UI built yet) would not retroactively update existing Applications' copies. Acceptable for now since there's no Applicant-edit surface yet either.

## Bug caught and fixed during this build
`016_applicants.sql`'s RLS policies called `public.is_ops_admin()`, which had EXECUTE revoked from `authenticated` by an earlier hardening pass (`004_harden_rls_execute.sql`) — every other policy in this project correctly calls `private.is_ops_admin()` instead. This made every Dashboard load fail silently (RLS filters rather than erroring) with the Applicants section always empty. Fixed in `017_fix_applicants_policies_private_is_ops_admin.sql`, applied and re-verified live.

## Ops-advisor review (same day) — two blockers found and fixed
Dispatched an Opus agent to review the relation from an ops/underwriting-integrity angle, as the user requested. It found:
- **`applicants` had RLS enabled with no DELETE policy at all** — `createLead`'s rollback (`.from('applicants').delete()` when the paired Application insert fails) matched zero rows and returned no error (RLS filters, doesn't raise), so *every* such failure left a permanent phantom Applicant with zero Applications. Fixed in `018_applicants_delete_policy_and_phone_index.sql` (own-or-ops delete policy, same pattern as every other table); `createLead` now checks the returned row count and logs if the rollback itself ever silently fails.
- **`createApplication` set the new lead's `agent_id` to the *caller's* id, not the Applicant's owning agent's id.** Since the Applicants dashboard card shows every partner's Applicants to an `ops_admin` viewer, this meant ops could graft a lead onto a partner's book that the partner would never see (the count would even differ by viewer). Fixed by inheriting `applicant.agent_id` instead — combined with the pre-existing `leads_insert_own` policy (`agent_id = auth.uid()`, no ops carve-out, confirmed no such carve-out exists anywhere in the migrations), this now makes an ops attempt fail closed with an RLS error rather than silently succeeding. Also hid the "+ New application" link on the dashboard, and guarded the route itself with a redirect, for anyone who isn't that Applicant's own agent — avoids a dead-end form fill that only fails at the very end.
- Verified live: forced a DB-level failure (invalid `loan_type` bypassing client validation) after the Applicant insert succeeded — confirmed the Applicant is now actually deleted (previously it would have silently survived).
- Backfill checked directly: zero orphan Applicants, zero same-agent collisions from the original 1:1 migration (moot at today's single-lead data volume, but the query is worth re-running before ever trusting a larger backfill of this shape).
- Not fixed, logged as follow-ups (not blocking, per the review's own recommendation): Applicant list sort order is currently meaningless (`applicants.updated_at` is never bumped by `createApplication`); no rollup of one Applicant's total exposure across their Applications; no dismissible "a file may already exist for this number" hint at New Lead time to catch accidental duplicate Applicants for a repeat customer (the explicit-only design's known trade-off, called out in the original decision above).
