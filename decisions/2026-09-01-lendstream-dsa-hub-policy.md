## Decision: Build the Policy tab as an authoring/browsing repository only — a curated `policies` table with jsonb parameter groups, single-actor versioning, and (after a mid-build correction) open-to-everyone drafting with ops-admin-only publish control

## Context
The user attached a full enterprise "Configurable LOS Policy Engine" requirements sheet and asked for three sub-views under the Policy tab: Live policy (active policies, click through to every configured param), All policy (every policy regardless of status), and Create policy (configure params). The reference document itself describes a much larger system: rule-evaluation engine, Decision-tab wiring, agent-assisted Auto Run, maker-checker approval chains, immutable audit trails — but its own scope table lists "Policy authoring UI and backend policy repository" as in scope and "Manual Run and Auto Run from Decision tab" as out of scope / a downstream dependency. That matched the user's literal ask closely enough to use as the scope boundary rather than building the full document.

Built via an Opus subagent (user explicitly authorized "you can use opus support"), given the doc's relevant sections, this app's existing conventions (`ProductsWorkspace.tsx`, `AddLenderProductForm.tsx`, the `private.is_ops_admin()` RLS gotcha), and hard constraints against building the rule engine / Decision-tab wiring / Auto Run / maker-checker. Reviewed the actual diff afterward rather than trusting the self-report alone.

Midway through review, the user sent a follow-up: "let every user has access to policy creation" — the original build had gated the entire Create tab (and `createPolicy` itself) to `ops_admin`. That gate is removed; see the RLS section below.

## Alternatives considered
1. **Build the full requirements sheet** (rule engine, scorecards, Auto Run, maker-checker, Decision-tab integration) — rejected. That's a multi-month project the sheet itself treats as a separate phase; the user asked for three sub-views, not a decision-execution platform.
2. **Store every field literally, as SQL columns** — the reference doc's Section 6 lists roughly 150 distinct parameters across nine groups. Rejected as impractical; would produce an unmaintainable table and a form nobody would finish filling out.
3. **A curated, bounded parameter set in structured `jsonb`** — chosen. Six groups (applicant, financial/affordability, bureau/repayment, collateral, pricing, decision-and-documents) with real representative fields per group, typed as first-class TypeScript interfaces (`PolicyParams` and friends) rather than an untyped blob. `jsonb` over columns because the group list is expected to grow and nothing queries into it server-side yet — if that changes, promoting specific fields to real columns is a normal follow-up migration, not a redesign.
4. **Full maker-checker / immutable versioning with a separate Approver role** — rejected as fiction for this app: only `dsa_partner` and `ops_admin` exist. Instead: `policy_code` is the stable identity, `version` increments, and a published version is never edited in place — `duplicatePolicyAsNewVersion` copies it into a new DRAFT. `activatePolicy` retires whatever other version of the same `policy_code` was live, in one call — a simplified, single-actor stand-in for the reference sheet's effective-dating control (its Section 10), not the full approval chain.
5. **RLS: ops-only everything vs. open drafting** — the first build gated INSERT to `ops_admin`, mirroring the family-level `products` table. The user then asked for open creation. Landed on: INSERT and SELECT open to any authenticated user (migration 028), UPDATE/DELETE (activate/deactivate/duplicate) still ops-admin-only. This isn't a full reversal to the `lender_products` open-everything precedent — it's closer to the reference sheet's own Policy Author (drafts, can't publish) vs. Policy Approver/Admin (publishes) split, which happens to fit this app's two-role model better than either extreme.

## Reasoning
Scoping to authoring/browsing only follows the requirements document's own boundary rather than contradicting it, and matches exactly what was asked. Curated jsonb groups keep the form and detail view finishable and real (every field genuinely configurable and displayed, no filler) without pretending to be the full spec. Single-actor versioning preserves the spec's core principle — a published version is never silently mutated — without inventing a role this app doesn't have. The open-create / ops-only-publish RLS split, reached after the user's correction, turned out to fit the two-role model more precisely than the original all-ops-only gate: anyone can propose a credit box, only ops can put it live or take it down.

## Trade-offs accepted
- No rule-evaluation engine: nothing in this app checks an application against a policy's params yet. The Decision tab is untouched. This is consistent with the reference sheet's own scope table, but it means a "policy" here is reference configuration, not yet an enforced credit box.
- No maker-checker / approval audit trail beyond `created_by`/`activated_at`/`change_reason`. Acceptable for this app's two-role model; would need a real Approver role and an audit-events table if the bank later wants that separation.
- Any signed-in user (including a `dsa_partner`) can now create policy drafts. A draft is inert until an ops admin activates it, so this doesn't let a partner make a credit-box decision live on their own — but it does mean the "All policy" table can accumulate drafts from anyone. No draft-cleanup/expiry mechanism exists yet.
- `priority` is stored and shown but nothing consumes it — surfaced honestly in the UI copy ("nothing consumes it yet") rather than implied to do something it doesn't.
- Collateral params are stored for every product but only meaningful (and only shown) for HL/LAP/WC — a PL/BL policy's collateral group is always empty by design, not a gap.
