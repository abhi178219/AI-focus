## Decision: Patched two privilege-escalation paths found by an independent review before building further app code, and added four cheap-now schema fields while tables are still empty

## Context: After applying the initial schema/RLS migrations, an independent Opus-model review of the whole process (brainstorm → decision → plan → implementation) was requested. It found the applied `handle_new_user()` trigger trusted client-supplied `role`/`clinic_id` from `raw_user_meta_data` (a self-signup could claim `role: 'doctor'` and read the whole clinic), and the `profiles_update_self` RLS policy only restricted which *row* a user could update (`id = auth.uid()`), not which *columns* — so any authenticated user could `update profiles set role='doctor'` on their own row. See the full review for the complete set of findings (not persisted verbatim — see below).

## Alternatives considered:
- Trust `raw_user_meta_data` for role/clinic_id but disable public signup in Supabase project settings as the only safeguard, vs. also hardening the trigger itself to ignore client-supplied role regardless of signup settings.
- Column-level Postgres grants to restrict self-service profile updates, vs. a `BEFORE UPDATE` guard trigger.

## Reasoning: Relying solely on a dashboard toggle (which this session has no API access to verify or set) as the only defense against role self-elevation is fragile — the fix needed to hold even if that setting is ever wrong. `handle_new_user()` now always inserts new profiles as `role='patient'` with `clinic_id` resolved server-side (single clinic in v1), never from metadata; elevating to `doctor`/`staff_admin` requires an explicit follow-up `UPDATE` from a service-role client (RLS-bypassing, only reachable from trusted server code — the invite action and seed script). Column-level `GRANT`/`REVOKE` was simpler than a guard trigger for restricting self-service profile edits to `full_name`/`phone` only.

Also added, since the tables are still empty and these are far cheaper now than as a later data migration: `vitals_readings.reading_group_id` (atomic pairing for compound readings like BP, replacing the fragile "match by `recorded_at`" approach), `patients.allergies` / `patients.other_medications_notes` (highest-yield missing safety fields in any prescribing flow), `profiles.registration_number` (expected on an Indian prescription), `prescription_items.route` (disambiguates oral vs. subcutaneous dosing).

## Trade-offs accepted: Public signup should still be explicitly disabled in the Supabase dashboard as defense in depth — this session cannot verify or set that via available tools, so it's on the user's setup checklist. Bigger structural findings from the same review (single `clinic_id` on `profiles` vs. a `clinic_memberships` join table for doctors who work at more than one site; whether all three portals belong in v1 at all) are deliberately not resolved by this decision — they're being brought back to the user rather than decided unilaterally, since they reopen scope/architecture calls already made explicitly in [2026-08-02-hospital-crm-mvp-scope.md](2026-08-02-hospital-crm-mvp-scope.md).
