## Decision: The app's first public, unauthenticated write path (consent capture, document upload) is authorised by an unguessable bearer token alone, resolved server-side on every request, with no RLS policy ever granted to the `anon` role

## Context
The user asked for two customer-facing capabilities on the application page: a way to send a customer a consent form to accept online (replacing the "CRM sync" card, which reported on an integration this app doesn't have, with a consent status + audit trail), and a way to send a customer a link to upload their own documents. Both necessarily mean a person with no account and no session performing a real write (consent decisions, an uploaded file) against this app's database — something nothing in this codebase had done before.

## Alternatives considered
1. **Grant `anon` a scoped RLS policy on the relevant tables** (e.g. "insert into `applicant_consents` where some token column matches") — rejected. Any RLS policy readable by `anon` is also reachable by anyone calling Supabase's REST API directly with the publishable key, bypassing the Next.js app entirely. A policy expressive enough to be useful (matching a token to a row) is also expressive enough to enumerate or probe through repeated direct API calls, with no application-level control over that traffic at all.
2. **A short-lived signed URL/JWT baked with the lead/applicant id inside it** — workable, but adds a signing-key management surface and a decode step to get right, for no real benefit over the option below.
3. **An unguessable token row (`customer_links`), validated exclusively inside server actions using the service-role client, with zero `anon` RLS grant on the table** — chosen. The token is a 122-bit random UUID minted by Postgres itself (`gen_random_uuid()` as the column default, never touched by application code before it exists). Holding it is the entire authorisation. Every public server action re-resolves it independently as its first step — token shape, row lookup, purpose match, expiry — and scopes every subsequent read/write to the `lead_id`/`applicant_id` that row names, never to anything a public request supplies itself. The service-role client that makes this possible is confined to one file (`app/actions/publicSubmissions.ts`), kept structurally separate from the authenticated actions (`app/actions/customerLinks.ts`) so the trust boundary is visible without reading either file closely.

## Reasoning
Option 3 keeps the actual authorisation logic in one place, in application code that can be read, tested, and reviewed line by line — rather than distributed across RLS policy expressions that are easy to get subtly wrong and hard to unit-test. It also means the *only* way this feature can misbehave is a bug in `publicSubmissions.ts` itself; the database has no independent opinion that a public caller is allowed to do anything, which removes an entire category of "the RLS policy was almost right" failure mode this project has already hit twice this session with `is_ops_admin()`.

Two attribution choices followed from tables this app already had: a link-captured consent is stamped `captured_by = customer_links.created_by` (the sending agent — `applicant_consents.captured_by` is `not null references profiles(id)` and a customer has no profile row, so the agent is the honest accountable party) with `channel = 'Consent link'` distinguishing it from a hand-recorded capture; a link-submitted document gets `uploaded_by: null` (the column was already nullable), honestly representing "not uploaded by a system user" rather than a fabricated attribution.

## Trade-offs accepted
- No rate limiting or CAPTCHA on either public endpoint. Token unguessability (122 bits) is the sole control against brute force; a 20 MB per-file cap on uploads is plain input validation, not throttling, and doesn't address a flood of small requests. Acceptable for now given the token space; would need real rate limiting before this app handled meaningfully adversarial traffic.
- Links are not single-use — a customer may reopen a link within its 7-day window and submit again, recording fresh rows rather than editing old ones. Chosen deliberately (a changed mind is itself part of the record) but means a link, once sent, keeps working for anyone who has it for the full window; the UI tells the sending agent this explicitly ("send it only to the customer").
- The public upload page reuses the lead-level `documents` table and its extraction pipeline path is untouched — a customer-submitted document goes through the same downstream OCR/extraction flow as any other, with no distinct handling for the fact that it arrived unauthenticated. This was in scope (reuse, not rebuild) but is worth knowing if extraction trust assumptions ever change.
