## Decision: Added a dedicated "ITR" analytical tab (positioned between Banking and GST), built by an Opus subagent from a detailed credit-manager framework the user supplied — income trend with sudden-jump detection, nature-of-income/presumptive-taxation read, profit computation, tax compliance, turnover cross-checks against GST and bank statement documents, assets/liabilities, evidence-only red flags, and a product-wise focus note.

## Context
User: "In the application details, next to banking sub section, I need to introduce a ITR section when the users/RM upload the ITR copies... I need to keep it insightful as well as make it easy for anyone to analyze this information," and supplied a detailed real-world credit-manager ITR-reading framework, explicitly asking to "take opus assistance and build a section."

The existing `ITR` document type and extraction schema were placeholder-thin (`assessment_year`, `gross_total_income`, `tax_paid` only) — `financials()` already had a `docOf(documents, 'FINANCIAL_STATEMENT') ?? docOf(documents, 'ITR')` fallback and a multi-year `years[]` pattern, but nothing fed it a real ITR shape, so an ITR-only file always rendered "Not scored" there. `DOC_TYPE_LABEL.ITR` is `'ITR (3 years)'` — the app already expected a single upload to contain multiple years, same as how one bank statement PDF is parsed month-by-month.

## Alternatives considered
- Expanding the existing "Financials" tab instead of adding a new one — rejected: the user explicitly asked for a section positioned "next to banking," i.e. a distinct tab, not a rework of Financials (which stays untouched and still falls back to ITR data for its own generic P&L/ratio view — the two tabs read the same source document through different lenses without conflicting).
- Building this myself directly rather than delegating to Opus — rejected per the user's explicit "take opus assistance" instruction. Dispatched a single, comprehensively-briefed Opus agent (given the full credit-manager framework verbatim, the exact `SectionView`/`docOf`/formatting-helper patterns from `banking()`/`gst()`/`financials()` as models, and hard constraints) to design and write the code, since schema and section-builder had to agree on field names exactly and splitting that across two agents risked a mismatch.
- Wiring ITR into the deterministic rules engine's composite score (a 5th pillar) — explicitly out of scope, instructed to the agent directly: the four scored pillars (BANKING/BUREAU/COLLATERAL/GST) are unchanged, matching precedent (FINANCIALS/BUSINESS/STOCK are already informational-only tabs with their own local `band` that doesn't feed the composite score).

## Reasoning
- `lib/ai/extractionPrompt.ts`: `itrSchema` redesigned with a nested `itrYearSchema` (oldest-first `years[]` — assessee category, ITR form, presumptive flag/section, full income-by-head breakdown, profit computation lines, tax-compliance fields, balance-sheet block) plus top-level headline fields mirroring the latest year, matching the `financialYearSchema`/`financialStatementSchema` precedent exactly. `FIELD_HINTS.ITR` rewritten to match in the same explicit, comma-separated style as the existing `BANK_STATEMENT`/`FINANCIAL_STATEMENT` hints.
- `lib/decision/sections.ts`: new `itr(lead, documents)` function (~620 lines), added to `SectionCode` and `buildSections()`. Every credit-manager point from the brief is represented: income trend (with an explicit "sudden step-up in the year before application" detection — a ≥50% latest-year jump the earlier years' average growth doesn't support — flipped to a caution band rather than read as strength), nature of income + presumptive-taxation nuance, profit computation with a cash-profit add-back shown "for reference — whether it is allowed as eligible income is lender policy," tax compliance (filing timeliness, revisions, outstanding demand), turnover credibility cross-checked against `docOf(documents, 'GST_RETURNS')` and `docOf(documents, 'BANK_STATEMENT')` when either is on file (each cross-check names plainly when the comparison document isn't uploaded yet, rather than silently omitting the row), assets/liabilities with a negative-net-worth flag, and a product-wise focus note keyed off `lead.loan_type`. Red flags are computed strictly from what the parsed data actually evidences — never asserted speculatively — and the whole card is withheld (not shown as "clear") when no ITR is on file at all, since "no red flags" would itself be an unevidenced claim about a document nobody has read.
- `components/shared/LeadDetail.tsx`: `{ key: 'itr', label: 'ITR' }` added to `TABS` immediately after `banking`, and `itr: 'ITR'` added to `SECTION_TABS`.
- **A real pre-existing bug found and fixed during my own independent verification** (not introduced by the agent — it correctly left `SectionPanel.tsx` untouched per instruction): the shared chips/knockouts card in `SectionPanel.tsx` showed "Clears policy — no knockouts." whenever `section.knockouts` was empty, *regardless* of whether `section.chips.items` had real entries — meaning the ITR tab's Red Flags card rendered that reassuring line directly above 7 actual flagged items, a direct contradiction. Fixed the conditional so the "clear" line only shows when there is truly nothing to flag in either list; verified the genuinely-clear case (Bureau's "Adverse records" card with zero adverse records) still renders correctly.
- Verified live end-to-end on a temporary test lead (never touching real data): inserted a synthetic-but-realistic two-year ITR document (presumptive 44AD, a deliberate 175% income jump, late/revised filing, ₹50k outstanding demand, negative net worth) plus a mismatched GST return and a cash-heavy bank statement, and confirmed every computed figure, band, and red flag fired correctly and matched hand-checked arithmetic — then deleted all test data. Also confirmed the empty-state ("ITR not on file yet") renders correctly and honestly on the real, unmodified "Abhishek" lead, which has no ITR uploaded.

## Trade-offs accepted
- No reconciliation against Form 26AS/AIS or TDS reported by customers — the app has no 26AS/AIS document type to compare against, so only the GST and bank-statement cross-checks are computed. `tds_credit` is captured and displayed but not cross-checked against anything.
- "Business income not matching the stated business activity" (one of the listed red flags) is not computed — it would need the ITR's business/nature-of-business code compared against `lead.industry`, which the schema doesn't currently carry at the return level.
- No `capacity` (implied eligible income) figure is shown for the ITR tab — cash profit (net profit + depreciation + remuneration add-backs) is displayed for reference only, deliberately not converted into a lender-facing capacity number, since that would read as feeding the credit decision, which is explicitly out of scope for this pass (only GST's own section computes an implied capacity today).
- `tsc --noEmit` is clean; no database migration was needed (extracted ITR data lives in the existing generic `documents.extracted_json` column, same as every other document type).

## Supersedes
None — additive. Extends the section model established across [2026-08-22-lendstream-dsa-hub-prototype-fidelity-rebuild.md](2026-08-22-lendstream-dsa-hub-prototype-fidelity-rebuild.md)'s "each analytical section is derived from a real parsed document" pattern to a new document type.
