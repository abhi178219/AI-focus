## Architecture facts worth remembering
- **LLM only extracts; a deterministic rules engine (`lib/decision/rulesEngine.ts`) computes score/verdict.** Never let the LLM output the final PASS/REFER/DECLINE directly — auditability requirement.
- Two roles only: `dsa_partner` (own leads only) and `ops_admin` (sees all). No multi-tenant/clinic_id equivalent — flat org.
- Full Aadhaar numbers are never extracted or persisted (only last 4 digits) — see `lib/ai/extractionPrompt.ts::redactAadhaar`, applied to `documents.ocr_text` for `AADHAAR`-type uploads too, not just the structured JSON.
- `documents.extraction_confidence` is a schema-completeness heuristic (fraction of expected fields populated), not a calibrated model confidence — don't present it as one.
- Pipeline runs synchronously inline in the upload/parse server actions (`app/actions/pipeline.ts`) — fine for single-user local dev, will need a background job before multi-user scale.
- Band thresholds (reused everywhere — pillar scores, composite score): STRONG≥80, GOOD≥65, MODERATE≥50, WEAK≥35, else CRITICAL. Verdict: any knockout → DECLINE; else STRONG/GOOD→PASS, MODERATE→REFER, WEAK/CRITICAL→DECLINE.

## Verified end-to-end (2026-08-22)
Manually tested the full document pipeline with a real synthetic salary slip PDF (generated via macOS `cupsfilter`, OCR'd via `pdftoppm`+`tesseract`, extracted via live Ollama call through the actual `processDocument` server action) — extraction was 100%-confidence correct, and the rules engine produced a mathematically-verified-correct FOIR/EMI calculation (PASS, GOOD, composite 77). Also verified: `handle_new_user()` trigger correctly assigns `dsa_partner` role regardless of signup input; RLS blocks cross-agent access (storage path + lead ownership checks).

## Environment quirks discovered
- Supabase free-tier project Auth has a low email-send rate limit — real self-signup email confirmation gets rate-limited quickly during dev/testing. Not a bug; the seed script sidesteps it entirely via `supabase.auth.admin.createUser({ email_confirm: true })`, which sends no email.
- `SUPABASE_SERVICE_ROLE_KEY` is deliberately not exposed via the Supabase MCP tools — must be fetched from the dashboard (Project Settings → API) and pasted in manually. Needed for `scripts/seed.ts` and any future admin/role-elevation server actions.
- Model speed on this Mac's CPU varies a lot by size: `qwen2.5:7b-instruct` took 60–120+ seconds per generation; switching to `gemma3:4b` (2026-08-22) cut that to ~10–20 seconds for the same case-narrative/Copilot/extraction calls, with comparably accurate structured JSON output in the (small-sample) testing done here. Any new AI feature still needs a visible pending state regardless of model (already built into `NarrativeCard`/`CopilotPanel`) — don't assume a fixed latency.
- Next.js Browser-pane automation quirk (not app-specific): after `navigate()`, the first `computer` click needs a `screenshot` call first to establish the coordinate frame, or the click silently no-ops.

## AI Copilot chat (2026-08-22, design reviewed by Codex before building)
- Fixed allowlist of 5 tool actions in `lib/copilot/schema.ts` (`move_lead_stage`, `create_lead`, `request_crm_sync`, `add_interaction_note`, `share_quote`) — no verdict/disbursed_amount/bank_assigned mutation exists as a tool at all, so the LLM cannot touch them regardless of prompt.
- Every proposal requires explicit user confirm/cancel in the UI before `confirmCopilotAction` runs, and that action always uses the normal RLS-scoped `createClient()` — never the service-role client — so a confirmed Copilot action can only do what the signed-in user could already do by hand.
- Zod gotcha: `z.discriminatedUnion('type', [...])` throws at schema-*definition* time (not parse time) if two branches share the same literal value on the discriminator key — breaks every page that transitively imports the module. Use a plain `z.union([...])` when multiple branches legitimately share the outer discriminator (here, 5 different `action` values under one `type: 'proposal'`).

## Minimal lead capture + document auto-fill (2026-08-22)
See [2026-08-22-lendstream-dsa-hub-minimal-capture.md](../../decisions/2026-08-22-lendstream-dsa-hub-minimal-capture.md). Lead creation now only takes client_name/phone/loan_type/requested_amount — everything else (income, tenure, property, co-applicant, CIBIL, bank) is filled in later via `EditApplicantForm` (`app/actions/leads.ts::updateLeadDetails`) or pulled from a parsed document via the "Apply to lead" button (`app/actions/applyFields.ts::applyExtractedFields`), which only ever fills currently-null fields — never overwrites. Live-tested full loop: minimal-capture lead → manual income/tenure entry → real valuation-report upload → OCR+LLM extraction (100% accurate) → apply-to-lead → assessment (REFER/61/MODERATE, FOIR 38.9% — hand-verified correct).

Also cleared all seeded leads/documents/assessments/interactions/offers from the live Supabase project per user request, so the app now starts empty. Kept: `products`/`commission_slabs` (functional reference data, not "dummy leads" — assessment can't run without a product to score against) and the demo login accounts (`agent1-4@rupeeboss.demo`, `ops1-2@rupeeboss.demo`, password `DemoPass123!`) so access isn't lost — `scripts/seed.ts` can still repopulate demo data on request.

## Applicant → Application relation (2026-08-31)
See [2026-08-31-lendstream-dsa-hub-applicant-application-relation.md](../../decisions/2026-08-31-lendstream-dsa-hub-applicant-application-relation.md). New `applicants` table (RLS mirrors `leads`) sits above `leads`, HubSpot Contact→Deals style — every `leads` row now has a required `applicant_id`. `createLead` creates one Applicant + one Application together every time; a second Application under an existing Applicant is only ever added explicitly via `createApplication`, reached from that Applicant's row on the Dashboard's new "Applicants" card (`/partner/applicants/[id]/application/new`) — no auto-matching by phone number. **RLS gotcha specific to this project**: policies must call `private.is_ops_admin()`, not `public.is_ops_admin()` — the public wrapper had EXECUTE revoked from `authenticated` by `004_harden_rls_execute.sql`, and calling it from a new policy fails RLS silently (no error surfaced to the query, just zero rows) unless you check Postgres logs / `console.error` the query result explicitly.

The New Lead modal (`components/shared/NewLeadModal.tsx`) was also rebuilt for pixel fidelity against the actual prototype file (still at the path above) — sizes/colors/copy sampled via `javascript_tool` computed-style extraction, not estimated from a screenshot. Reusable technique for any future "make X match the prototype" request: `cp` the prototype html into the scratchpad, serve with `python3 -m http.server`, navigate the Browser pane to it, and pull `getComputedStyle` on the real elements rather than eyeballing a screenshot.

## Per-section AI summaries (2026-09-01)
Generalises the existing single "AI case summary" pattern (`leads.case_narrative` + `NarrativeCard.tsx` + `app/actions/narrative.ts`) to one summary per (lead, section) instead of one per lead. New `section_summaries` table (migration 025, RLS mirrors every other lead-scoped table's own-or-ops pattern). New `sectionFacts()` helper in `sections.ts` flattens whatever a built `SectionView` populated (metrics/hero/signals/panels/chips/notes/conduct/capacity/knockouts) into plain text — the exact figures already on screen, never raw `extracted_json` — so the LLM prompt can never see a number the app hasn't already verified and displayed. `generateSectionSummary` (`app/actions/sectionSummary.ts`) calls the same local Ollama endpoint as `generateCaseNarrative`, on demand via a Generate/Regenerate button (`SectionSummaryCard.tsx`), only offered when `section.status === 'ready'` (nothing to summarize from a section with no document on file). Wired once into `SectionPanel.tsx` — since every analytical tab (Banking, ITR, GST, Bureau, Financials, Business, Stock, Collateral) renders through that same shared component, all eight got the capability from one change. `LeadDetail.tsx` fetches only the active tab's own summary row (not all eight) per page render. Verified live: real gemma3:4b generation, factually accurate against the displayed figures, persisted and reloaded correctly from the new table — then test data removed. Local `ollama serve` was not running at the start of this session's verification pass; started manually to test the real call (the app's own dev-server keep-alive script only manages the Next.js process, not Ollama).

Also removed the ITR tab's "What this product needs from the ITR" prose block (and its `ITR_PRODUCT_FOCUS` lookup) per explicit user request — the AI summary card now sits in that visual position instead.

## Applicant + Key Personnel edit capability (2026-08-31)
Added click-to-edit (same pattern as `ApplicantPanel.tsx`'s lead-level Applicant tab) to `ApplicantIdentityCard.tsx` — covers name/company-name, PAN, mobile, email, address, pincode, via new `updateApplicant` action (`app/actions/applicants.ts`). Since a key person IS a full Applicant, visiting their own detail page and clicking Edit there works identically — no separate code path needed. Key personnel's `designation` (the one field that lives on the association, not the person) is edited inline per-row on the company's Key Personnel list (`KeyPersonnelList.tsx`, hover-to-reveal pencil icon) via new `updateKeyPersonnelDesignation`.

**RLS gap found and fixed while wiring this up**: migration 023 added select/insert/delete policies on `key_personnel` but missed update — editing a designation silently failed ("Could not save — you don't have access") with 0 rows affected until `024_key_personnel_update_policy.sql` added the missing policy. Caught immediately during verification, not left in place.

**Data mishap during this session's own verification, caught and fixed**: while testing the Company/Key-Personnel flow, a stray click during browser automation flipped the real "Abhishek" applicant's `entity_type` to `'COMPANY'` (all other fields — name/phone/email/PAN — were untouched). Caught immediately on the next verification pass (an unexpected "Company" badge on real data), reverted via direct SQL (`entity_type` back to `'INDIVIDUAL'`), and confirmed no `key_personnel` rows were ever attached to it. Flagged to the user rather than silently fixed. Lesson: when verifying a feature that mutates real, pre-existing records (not a purpose-created test row), re-check the actual production row immediately after each test pass, not just at the end.

## Applicant detail page (2026-08-31)

## Applicants got a dedicated searchable list page (2026-08-31)
`/partner/applicants` (`app/partner/applicants/page.tsx`) — a proper table (`ApplicantsTable.tsx`) with its own debounced search bar (`ApplicantsFilterBar.tsx`, 300ms, filters name/phone/email via `.or(...ilike...)`, URL-driven via `router.replace` so the search is shareable/bookmarkable). The Dashboard card is now a lightweight preview (top 5, `Avatar` + name + phone/email + application count, no nested detail), each row linking into the full list pre-filtered on that applicant's phone (`/partner/applicants?q=<phone>`), with a "See all" link in the header — same pattern as "Recent Leads" → `/partner/leads`. Not added to the sidebar nav (kept scope to what was asked); reachable via "See all" only.

## Per-lender-product document requirements (2026-08-31)
`lender_products.required_documents` (text[], migration 020) — a checkbox grid next to "Credit-box note" on the "Add a new product" form (`AddLenderProductForm.tsx`), reusing `DOC_CATEGORIES`/`DOC_TYPE_LABEL` from `lib/documentCategories.ts` (same source of truth the document-upload dropdown uses) and whitelisted server-side the same way. Distinct from `products.required_documents` (the product family's baseline) — a specific lender within a family can require more documents than the family's default (e.g. one bank wanting a valuation report others don't). Not in the prototype (checked directly — its add-product form has no document fields at all); this was a genuine new feature request, not a fidelity fix.
