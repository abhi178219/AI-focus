## Architecture facts worth remembering
- **LLM only extracts; a deterministic rules engine (`lib/decision/rulesEngine.ts`) computes score/verdict.** Never let the LLM output the final PASS/REFER/DECLINE directly — auditability requirement.
- Two roles only: `dsa_partner` (own leads only) and `ops_admin` (sees all). No multi-tenant/clinic_id equivalent — flat org.
- Full Aadhaar numbers are never extracted or persisted (only last 4 digits) — see `lib/ai/extractionPrompt.ts::redactAadhaar`, applied to `documents.ocr_text` for `AADHAAR`-type uploads too, not just the structured JSON.
- `documents.extraction_confidence` is a schema-completeness heuristic (fraction of expected fields populated), not a calibrated model confidence — don't present it as one.
- Pipeline runs synchronously inline in the upload/parse server actions (`app/actions/pipeline.ts`) — fine for single-user local dev, will need a background job before multi-user scale.
- Band thresholds (reused everywhere — pillar scores, composite score): STRONG≥80, GOOD≥65, MODERATE≥50, WEAK≥35, else CRITICAL. Verdict: any knockout → DECLINE; else STRONG/GOOD→PASS, MODERATE→REFER, WEAK/CRITICAL→DECLINE.

## Environment quirks discovered
- Supabase free-tier project Auth has a low email-send rate limit — real self-signup email confirmation gets rate-limited quickly during dev/testing. Not a bug; the seed script sidesteps it entirely via `supabase.auth.admin.createUser({ email_confirm: true })`, which sends no email.
- `SUPABASE_SERVICE_ROLE_KEY` is deliberately not exposed via the Supabase MCP tools — must be fetched from the dashboard (Project Settings → API) and pasted in manually. Needed for `scripts/seed.ts` and any future admin/role-elevation server actions.
- Model speed on this Mac's CPU varies a lot by size: `qwen2.5:7b-instruct` took 60–120+ seconds per generation; switching to `gemma3:4b` (2026-08-22) cut that to ~10–20 seconds for the same case-narrative/Copilot/extraction calls, with comparably accurate structured JSON output in the (small-sample) testing done here. Any new AI feature still needs a visible pending state regardless of model (already built into `NarrativeCard`/`CopilotPanel`) — don't assume a fixed latency.
- Next.js Browser-pane automation quirk (not app-specific): after `navigate()`, the first `computer` click needs a `screenshot` call first to establish the coordinate frame, or the click silently no-ops.

## AI Copilot chat (2026-08-22, design reviewed by Codex before building)
- Fixed allowlist of 5 tool actions in `lib/copilot/schema.ts` (`move_lead_stage`, `create_lead`, `request_crm_sync`, `add_interaction_note`, `share_quote`) — no verdict/disbursed_amount/bank_assigned mutation exists as a tool at all, so the LLM cannot touch them regardless of prompt.
- Every proposal requires explicit user confirm/cancel in the UI before `confirmCopilotAction` runs, and that action always uses the normal RLS-scoped `createClient()` — never the service-role client — so a confirmed Copilot action can only do what the signed-in user could already do by hand.
- Zod gotcha: `z.discriminatedUnion('type', [...])` throws at schema-*definition* time (not parse time) if two branches share the same literal value on the discriminator key — breaks every page that transitively imports the module. Use a plain `z.union([...])` when multiple branches legitimately share the outer discriminator (here, 5 different `action` values under one `type: 'proposal'`).

## Policy tab: Live/All/Create policy workspace (2026-09-01)
The `/partner/policy` placeholder from earlier the same day is now a real feature. New `policies` table (migration 027): `policy_code` (stable identity across versions, uppercased on write) + `version` with a `unique (policy_code, version)`, plus `name/description/product/status/priority/effective_from/effective_to/change_reason/created_by/activated_at` and a `params jsonb` holding six curated parameter groups — applicant, financial, bureau, collateral, pricing, decision — typed for real as `PolicyParams` and friends in `lib/types.ts` (jsonb rather than columns because the group list is expected to grow and nothing queries into it server-side).

**Deliberate scope cut** versus the enterprise "Configurable LOS Policy Engine" requirements sheet the user attached: this is the *authoring and browsing repository only*. No rule-evaluation engine, no Decision-tab wiring, no Auto Run / agent policy-selection — the requirements sheet's own scope table lists "Policy authoring UI and backend policy repository" as in scope and "Manual Run and Auto Run from Decision tab" as out of scope / a downstream dependency, so the cut follows the document rather than contradicting it. Also no maker-checker approval chain: this app has exactly two roles (`dsa_partner`, `ops_admin`) and no separate Approver, so inventing one would have been fiction. `priority` is stored and displayed but nothing consumes it yet, and that's stated in the UI rather than implied away.

**Versioning is single-actor**: DRAFT → ACTIVE → INACTIVE. A published version is never edited in place — `duplicatePolicyAsNewVersion` copies it to a new DRAFT under the same `policy_code` at max(version)+1, so what was live at any point stays readable. `activatePolicy` publishes one version and flips any *other* ACTIVE row sharing that `policy_code` to INACTIVE in the same call, which is the simplified stand-in for the reference sheet's effective-dating control (section 10) without an approval step. `deactivatePolicy` is a plain pause (AC-10's "pause without code deployment"). All four actions check `profiles.role` server-side as well as relying on RLS, so the UI shows a sentence rather than a raw Postgres error, and check affected row counts rather than just the absence of `error` — the established discipline here, since RLS filters silently.

**RLS, revised mid-build per explicit user request** ("let every user has access to policy creation"): SELECT and INSERT are both open to any authenticated user (migration 028 drops the original ops-only insert policy) — anyone can author a DRAFT. UPDATE/DELETE stay ops-admin-only, so `activatePolicy`/`deactivatePolicy`/`duplicatePolicyAsNewVersion` remain gated — publishing, pausing and versioning a policy is still a credit/ops function even though drafting one isn't. This lands closer to the reference sheet's own Policy Author (drafts, can't publish) vs. Policy Approver/Admin (publishes) split than the original ops-only-everything build did. Policies call `private.is_ops_admin()` throughout for the write actions that still need it — the recurring gotcha in this project, since `public.is_ops_admin()` had EXECUTE revoked from `authenticated` in migration 004 and any policy calling it denies silently. Verified against the live project after both migrations: RLS enabled, insert is `auth.role() = 'authenticated'`, update/delete resolve to `private.is_ops_admin()`.

UI is one `PolicyWorkspace.tsx` with three URL-driven sub-view pills (`?view=live|all|create`), same shape and class idioms as `ProductsWorkspace.tsx`. **Live policy** shows only ACTIVE rows, grouped into a section per product (using the now-shared `LOAN_TYPE_LABEL`), each card carrying a short human-readable digest of the decision-relevant params (bureau cutoff / FOIR / amount band / LTV) rather than raw JSON. **All policy** is a table of every version regardless of status. **Create policy** renders `CreatePolicyForm.tsx` for everyone — the required-documents checkbox grid reuses `DOC_CATEGORIES`/`DOC_TYPE_LABEL` exactly as `AddLenderProductForm.tsx` does, and the collateral section renders conditionally on the selected product (HL/LAP/WC). `/partner/policy/[id]` renders every group in Card sections with "—" for anything unset, never a fabricated default, and shows Activate/Deactivate/Duplicate only to `ops_admin` viewers. Also de-duplicated `LOAN_TYPE_LABEL` while here — it had been copy-pasted identically into three files (`app/partner/page.tsx`, `app/partner/applicants/[id]/page.tsx`, `ApplicantsTable.tsx`) and is now exported once from `lib/types.ts`.

Live-verified end to end as `ops1@rupeeboss.demo`: created a draft (`TEST-PL-01`), confirmed the collateral section correctly disappears for Personal Loan, activated it (status flipped, `activated_at` stamped, Live policy showed it grouped under Personal Loan with a "1 live" count), confirmed All policy lists it, then deleted the test row directly via SQL. Confirmed the open-insert RLS change with a direct `pg_policy` query before testing.

## GST section revamp — credit-manager framework (2026-09-01)
Rebuilt the existing GST tab (`gst()` in `lib/decision/sections.ts`, ~500 lines) and its extraction schema around a detailed credit-manager framework, the same way `itr()` was built earlier the same day — and deliberately mirroring `itr()`'s helpers (`docOf`, `EMPTY_SOURCE`, `worstBand`, `BAND_POINTS`, `mean`/`stddev`, `sparseAxis`) rather than inventing new ones. `gstSchema`/`FIELD_HINTS.GST_RETURNS` in `extractionPrompt.ts` gained a registration/identity block (`gstin_status`, `constitution`, `principal_place_of_business`, `registration_date`, `additional_registrations_count`), a GSTR-1 composition block (B2B/B2C/export/interstate/credit notes), a GSTR-3B tax-payment block (liability, cash tax, ITC utilised/claimed, reverse charge, interest & late fees, tax carried forward), consistency inputs (`gstr9_annual_turnover`, `gstr2b_itc`) and self-stated compliance flags (`has_notices_or_mismatches`, `amendment_count`, `gstin_cancelled_or_suspended_note`). The per-period array kept the name `monthly_turnover` and the field `taxable_value` on purpose — `lib/decision/qualityFactors.ts` and `itr()`'s own GST cross-check both read them directly, so renaming would have broken two live readers for no gain — and gained `gstr1_taxable_value` / `gstr3b_taxable_value` / `tax_paid_cash` / `itc_claimed` / `filed_on_time` / `nil_return` per period. `gstin_status` is a plain `z.string()` and not a `z.enum`, matching every other constrained-vocabulary field in that file: a strict enum would fail the WHOLE extraction on a casing slip ("Active"), and `sections.ts` uppercases it anyway.

The tab is now organized around the framework's six groups: **registration & identity** (status banded as a real problem when CANCELLED/SUSPENDED, plus vintage in months derived from `registration_date` against a new `GST_POLICY.minRegistrationVintageMonths` = 12, so a recently created GSTIN reads as limited verifiable vintage however long the applicant says they've traded), **GSTR-1 turnover & mix** (period trend, B2B/B2C/interstate/export breakdown, credit-note ratio, reused concentration and stddev-volatility logic), **GSTR-3B & tax payment**, **consistency between returns**, **cash-flow quality**, and **compliance behaviour**. New `GST_POLICY` keys added, none removed or renamed: `minRegistrationVintageMonths`, `gstr1VsGstr3bTolerancePercent`/`gstr1VsGstr3bCriticalPercent`, `itcMismatchTolerancePercent`, `creditNoteWarnPercent`/`creditNoteCriticalPercent`, `cashTaxShareWarnPercent`, `suddenStepUpPercent`.

The cross-checks reuse `itr()`'s pattern exactly: `docOf(documents,'ITR')` for GST-vs-declared-turnover and `docOf(documents,'BANK_STATEMENT')` for GST-sales-vs-annualised-credits (credits annualised from however many statement months exist, same as `itr()` does), plus a `docOf(documents,'FINANCIAL_STATEMENT')` read for receivable days banded off the existing `BUSINESS_POLICY.cycle*Days`. Every one of them states plainly that the comparison document is missing rather than silently disappearing. GSTR-1-vs-GSTR-3B and GSTR-2B-vs-ITC-claimed are derived in code from the periodic array and the two ITC fields, never extracted as a pre-computed gap. The sudden-turnover-step-up detector mirrors `itr()`'s: last three periods against the earlier ones, flagged only when the step-up lands immediately before the application. Red flags are an evidence-only `chips` list — GSTIN cancelled/suspended, GSTR-1 » GSTR-3B, GST » ITR, GST » bank credits, sudden step-up, large credit notes, aggressive ITC against low cash tax, ITC beyond GSTR-2B, nil returns despite bank credits, buyer concentration, unfiled/late returns, tax carried forward, amendments, notices, additional GSTINs — each appearing only when the real parsed figures make it true, and **withheld entirely (not rendered as "all clear") when no GST document is on file**, exactly like `itr()`'s. The existing assessed-margin `capacity` calculation (GST_MARGINS grid x turnover x FOIR-on-margin, capped per `GST_POLICY.caps` for unsecured) is preserved verbatim; its `basis` text now carries the "turnover is sales, not profit — GST sales include output tax" caveat, and a matching one-line `notes` entry sits beside it (no standalone prose block — the generic AI-summary card covers narrative synthesis). The two existing knockouts are unchanged and a third was added for an inactive GSTIN.

**`lib/decision/rulesEngine.ts::gstPillar` was not touched, and neither was the PASS/REFER/DECLINE decision.** This is a display/analysis-layer change only. `extracted_json.turnover` stays a top-level number meaning annual turnover, because `gstPillar` reads it verbatim (as does `DecisionPanel.tsx`'s turnover triangulation) — the schema comment now says so explicitly so the next person restructuring it doesn't silently break the credit decision. Everything new the section computes is expressed through field kinds `sectionFacts()` already flattens (hero/subHero/metrics/signals/panels/chips/notes/capacity/knockouts/conduct), so the per-section AI summary picked up all of it with no change to `sectionSummary.ts` or `SectionPanel.tsx`. Verified by driving `buildSections()` on a synthetic adverse payload through `npx tsx` — 16 red-flag chips fired, two knockouts, `sectionFacts()` output complete — and on an empty document set, which still reports `status:'missing'` with chips and bandPanels withheld. `npx tsc --noEmit` clean.

## Applicant relationship layer: snapshot, consent, document vault, attribution, activity (2026-09-02)
The Applicant detail page (`/partner/applicants/[id]`) gained a relationship layer sitting *above* the per-application (`leads`) layer. Four new objects (migration 030), all `applicant_id`-scoped on purpose: `applicants.lead_source_channel`/`referring_partner` (attribution — the channel that brought a person in doesn't change when they come back for a second loan, so it belongs on the person, not on each file), `applicant_consents`, `applicant_documents` and `applicant_interactions`, plus a private `applicant-documents` storage bucket with the same `{agent_id}/{applicant_id}/{documentId}-{filename}` path convention `lead-documents` uses.

**Why each is applicant-scoped rather than lead-scoped.** `applicant_consents` is append-only — never updated in place; a fresh capture supersedes the prior one purely by having a later `captured_at`, so the record of what was agreed, when, and over which channel survives. An upsert would destroy exactly the thing a consent trail exists to preserve. `applicant_documents` is deliberately NOT `public.documents`: those are lead-scoped and feed the AI extraction pipeline, whereas a PAN card / Aadhaar / MOA-AOA belongs to the person forever and is stored and listed here, never parsed — no OCR, no status flow, no extraction trigger. `applicant_interactions` is deliberately NOT `public.interactions`: the Customer/Internal/Bank category split added the same day in migration 029 is specific to working *one* loan file (who the conversation was with, about that file), and has no meaning at the relationship level where every touchpoint is with the customer — so that split is intentionally absent here rather than copied.

**Snapshot computation — five deliberate judgement calls, made to resolve genuine ambiguity in the request.** All five are computed server-side in `page.tsx` from the already-fetched `apps` array (no re-fetch, no `calculateEmi`, nothing modelled). (1) *Active exposure* = sum of `disbursed_amount ?? requested_amount` over every lead where `stage !== 'DROPPED'` — real money out where known, the ask where not; dropped files represent no exposure at all. (2) *Existing EMI obligation* = `existing_emis` from the **single most recent** application only, **not summed** across applications, and the card says so on its own sub-line. `existing_emis` is the applicant's declaration of their *other* obligations at one point in time; summing it across three files would count the same external debt three times. This is a documented simplification, not an oversight — do not "fix" it into a sum. (3) *Relationship tenure* from the earliest lead's `created_at` to now, "X yr Y mo" / "X mo" / "Under 1 mo", with "New relationship" reserved for exactly one application created in the last 30 days rather than implied by a small number. (4) *Lifetime applications* is Won (`DISBURSED`) / Dropped (`DROPPED`) / **Active** (everything else). The third bucket is deliberately NOT called "Lost": this app's stage model has no terminal declined stage distinct from `DROPPED`, so a "Lost" bucket would be fiction — the card states this in a sub-line ("anything not disbursed or dropped is still active in the pipeline") rather than leaving the next reader to rediscover it. (5) *Repayment behaviour* renders an honest unavailable line — "this app captures loan origination, not loan servicing, so on-time / DPD history isn't tracked here yet" — even when Won > 0, as one stat line among several rather than a big empty-state block. No on-time / DPD figure is invented.

**UI**: five new components under `components/shared/` — `RelationshipSnapshotCard` (pure display, props computed in the page), `ConsentCenterCard` (current state per type with Granted / Not granted / **Not captured yet** — a missing row never reads as a refusal — plus an `isOwn`-gated capture form whose Decision select has no default, since a fabricated refusal is as wrong as fabricated consent), `ApplicantDocumentVault` (a compact type-select + file + Upload row; no drag-drop, no camera, no category grouping — all of which only earn their place on the lead-side uploader that actually extracts), `AttributionCard` (its own small card because it writes through its own `updateLeadSource` action, but reusing `ApplicantIdentityCard`'s exact click-to-edit pattern rather than inventing a third one) and `RelationshipActivityCard` (six channels, note, next-follow-up, reverse-chron list — intentionally far more compact than `ActivityPanel`, which was not touched). Actions live in one new `app/actions/applicantRelationship.ts`, all four checking `auth.getUser()`, validating every enum against its real vocabulary rather than falling back to a guess, and checking affected row counts (RLS filters silently). Small enrichment to the existing Active/Closed application rows: the neutral grey stage chip became the stage-coloured pill, reusing `STAGE_PILL_STYLES`/`STAGE_LABELS` exactly as `LeadHeader.tsx`/`LeadsTable.tsx` render them, so a Sanctioned file looks the same everywhere.

**RLS**: own-or-ops throughout, scoped through `public.applicants.agent_id` — select via an `exists` on the parent applicant; insert mirroring migration 004's corrected shapes (`documents_insert_via_lead` for consents/documents, i.e. an honest `captured_by`/`uploaded_by` stamp AND parent-applicant access; `interactions_insert_via_lead` for interactions, i.e. ops always, or `agent_id = auth.uid()` on an owned applicant). No update/delete policies on any of the three tables — append-only, same convention as `public.documents`. Storage policies mirror `lead_documents_select/insert_own_or_ops` with `public.applicants` checked on the second path segment; no update/delete policy there either. Every policy uses `private.is_ops_admin()` — the recurring gotcha in this project, since `public.is_ops_admin()` had EXECUTE revoked from `authenticated` in migration 004 and any policy calling it denies silently. Verified against `pg_policy` on the live project after applying: all eight new policies (six table + two storage) resolve to `private.is_ops_admin()`, none to the public one. `npx tsc --noEmit` clean.

## Customer-facing links: consent capture and document upload (2026-09-02)
The app's **first public, unauthenticated write path**. Two standalone pages — `/consent/[token]` and `/upload/[token]` — that a customer with no account opens from a link their RM sends them. Neither uses `AppShell`: no sidebar, no nav, nothing from the partner portal. `lib/supabase/middleware.ts` was not touched and did not need to be — `/partner/*` is the only auth-gated prefix, so any other route is already reachable with no session, by design.

**The security model, which is the whole point.** A `customer_links` row (migration `031_customer_links.sql`) is one capability handed to one customer for one lead, for seven days: `token uuid unique default gen_random_uuid()`, `purpose in ('CONSENT','DOCUMENT_UPLOAD')`, `lead_id`, `applicant_id`, `created_by`, `expires_at`. **The token is a bearer capability, not an identifier** — holding it is the entire authorisation, and it is the *only* thing a public request may name. Everything each public action then reads or writes is scoped to the `lead_id`/`applicant_id` recorded on the resolved row; there is no code path by which a visitor can say which lead or applicant they are acting on. The upload's storage path segment `{agent_id}` is read off the lead, never accepted from the form, so a public request cannot write into another agent's folder. The token is minted **only** by the column default — application code never generates one, so the unguessable value exists in exactly one place (122 bits either way; `gen_random_uuid()` in Postgres and `randomUUID()` in Node are the same strength, and using the default removes a second randomness source from the picture).

**There is deliberately NO anon RLS policy on `customer_links`.** The table's two policies (`customer_links_select_via_lead`, `customer_links_insert_via_lead`) are `to authenticated` only, own-or-ops through `public.leads.agent_id`, both via `private.is_ops_admin()` (the recurring gotcha — `public.is_ops_admin()` has EXECUTE revoked and any policy calling it denies silently). Had an anon policy existed, anyone could hit Supabase's REST API directly and enumerate or probe live links, bypassing the Next.js pages entirely. Instead, public access runs **exclusively** through `createServiceClient()` — its first real caller in this app — confined to `app/actions/publicSubmissions.ts`, behind a token check. Verified on the live project after applying: `pg_policy` shows exactly two policies, both `authenticated`, both resolving to `private.is_ops_admin()`, zero public/anon; and with a live row present, `set local role anon; select count(*)` returns **0** while the privileged role sees 1.

**Actions are split across two files because they run at different trust levels, and that should be visible without reading either.** `app/actions/customerLinks.ts` is the authenticated half (`createConsentLink` / `createDocumentUploadLink`) — normal `createClient()`, `auth.getUser()`, affected-row-count checks, applicant read off the lead rather than accepted from the caller. `app/actions/publicSubmissions.ts` is the public half, with **no auth check because there is no user**. All four of its exported functions (`getConsentPageData`, `submitPublicConsent`, `getUploadPageData`, `submitPublicDocument`) call the same unexported validator `resolveCustomerLink(token, expectedPurpose)` as their *first* step — token shape, row lookup, `expires_at > now()`, purpose match — and do nothing at all until it returns a row. Each re-validates independently: a token checked in one call proves nothing about the next, which is a separate request from an untrusted client, and a link may have expired between them. The validator is deliberately **not** exported: a `'use server'` export is a callable endpoint, and a token-validity oracle is exactly what this feature must not hand out. A bad token gets one flat string — "This link is invalid or has expired." — with no hint whether it was unknown, expired or for the other purpose, and no "did you mean". Public-facing failures never surface raw Postgres/storage messages. Token unguessability is the control; no rate limiting or CAPTCHA in this pass (a 20 MB upload cap is plain input validation, not throttling).

**Reuses `applicant_consents` rather than starting a second consent system.** A customer submitting the public form writes three new rows to the same append-only table `ConsentCenterCard`/`recordConsent` write — same `CONSENT_TYPES` vocabulary, same "a newer row supersedes without erasing" rule, so the applicant page's Consent Centre shows link-captured and hand-captured consents in one trail. The link is **not single-use**: within its window the customer may reopen it and answer differently, and that records fresh rows rather than editing old ones, so a change of mind is itself part of the record. No item on the form carries a default — an unanswered item blocks submission rather than being read as a refusal, the same discipline `recordConsent` applies, since a fabricated "no" is as wrong as a fabricated "yes".

**Attribution — the deliberate call.** `applicant_consents.captured_by` is `not null references profiles(id)` and a customer has no profile row, so a link-captured consent is stamped `captured_by = customer_links.created_by`: **the agent who generated and sent the link**. That is the honest reading, not a workaround — the agent is the accountable party for having sent it — and `channel` (free text) is set to `'Consent link'`, which is what visibly distinguishes these rows from a manual capture. Documents go the other way: `documents.uploaded_by` is already nullable, so a public-submitted document is inserted with **`uploaded_by: null`** — honestly "not uploaded by a system user" rather than attributed to a profile that didn't do it.

**Public pages leak nothing beyond their one flow.** The consent page shows a display name (first name for an INDIVIDUAL; the full stored name for a COMPANY, since the first word of "Sunrise Textiles Pvt Ltd" is not a name) and the three consent types with plain-language explanations of what each actually permits. The upload page shows the required document types (mirroring `LeadDetail.tsx`'s exact computation from the product catalogue's `required_documents`) and a bare "already received" list — **type and date only**, never a file name, storage path, id, or anything from another lead or applicant. Both pages are `force-dynamic` and `robots: noindex`.

**Where the CRM sync card went.** `ActivityPanel.tsx`'s sidebar "CRM sync" card — which reported on an integration this app does not have — was replaced by `ConsentStatusCard.tsx`. It reuses `ConsentCenterCard`'s exact status language (Granted / Not granted / **Not captured yet**, a missing row never reading as a refusal) in a narrower sidebar form with no capture form, adds an owner-gated "Send consent link" button, and puts the **full** consent history (every row, not just latest-per-type, newest first) behind a `useState` "View more" expander — the audit trail. `LeadDetail.tsx` fetches that history with the same query shape `app/partner/applicants/[id]/page.tsx` uses, scoped via `lead.applicant_id`, and passes it plus `isOwn` into `ActivityPanel` as new props. The Documents tab gained a small `UploadLinkCard` above `DocumentUploadForm`. Both link buttons share `CustomerLinkPanel`, which shows the generated URL in a plain read-only select-on-focus input — no clipboard API, since a field an agent can see the whole of beats a button claiming to have copied something. The origin is read client-side (`window.location.origin`) because a server action has no access to the request host; it only shapes the string handed back to that same agent and never influences which lead is touched. `npx tsc --noEmit` clean.

**First real usage, caught during the next session's verification (2026-09-04):** while confirming an unrelated change on Abhishek's applicant page, found real `applicant_consents`/`customer_links` rows — a CONSENT and a DOCUMENT_UPLOAD link genuinely generated and the consent one genuinely submitted (all three Granted), timestamped after the feature shipped and for a different lead than anything tested during the build. Left entirely in place — this is the feature working, not test residue — and confirmed via `customer_links` before touching anything.
