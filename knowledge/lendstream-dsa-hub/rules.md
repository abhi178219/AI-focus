# LendStream DSA Hub — confirmed rules

- Apply hospital-crm's RLS-hardening pattern to any new role/table from day one: `handle_new_user()` never trusts client-supplied role; role column is never client-writable (column-level GRANT/REVOKE); role elevation only via service-role client. Confirmed working via live signup test (2026-08-22).
- Any SECURITY DEFINER helper function used inside RLS policies must live in a non-PostgREST-exposed schema (`private`) with EXECUTE revoked from `anon`/`authenticated` on any public-schema copy — confirmed via independent Codex review catching this on the first pass (see `004_harden_rls_execute.sql`).
- Storage bucket path-ownership checks must validate every meaningful path segment (not just the top-level `auth.uid()` folder) — a two-segment path like `{agent_id}/{lead_id}/...` needs an EXISTS check that `lead_id` is actually owned by `agent_id`, or a user can write into another user's sub-folder.
- For OCR on financial/loan documents, prefer native `tesseract`+`poppler` binaries over `tesseract.js` — materially better accuracy, one-time `brew install` cost is worth it.
- On this Mac's CPU-only setup, prefer a ~4B-parameter Ollama model (`gemma3:4b`) over a ~7B one (`qwen2.5:7b-instruct`) for interactive features (Copilot chat, on-demand narrative generation) — cut latency from 60-120s to ~10-20s per call with no observed accuracy loss on clean synthetic test documents. Re-evaluate if real-world (noisier) documents show the smaller model struggling.
- Every lead-mutating server action must both check `getUser()` (redirect if absent) and check the mutation's returned row count (`.select('id')` after update/insert), not just check for a Postgres `error` — RLS silently filters out unauthorized rows rather than erroring, so `{ error: null, data: [] }` looks like success unless you explicitly check `data.length`. Caught by an independent Codex review on `updateLeadDetails`/`updateLeadStage` (2026-08-22); apply this pattern to any new mutation action.
- After a server action that calls `revalidatePath()` is invoked from a plain function call (not a `<form action>` or `useActionState`) inside a `startTransition`, also call `router.refresh()` client-side on success — don't rely on `revalidatePath` alone to guarantee the current route's already-rendered UI picks up the change. Caught on `ApplyFieldsButton` (2026-08-22), where applying document fields to a lead didn't visibly update the Applicant tab until manual navigation.
- Never map a document's extracted field onto a lead column if the field isn't actually a direct proxy for that column's meaning (e.g. bank statement `avg_monthly_balance` is not `monthly_income`) — even if the rules engine already uses it as a *scoring* fallback, writing it into the lead record presents it with false authority as verified data the user or an underwriter might trust at face value. Caught by Codex review (2026-08-22); removed from `app/actions/applyFields.ts`.
- **Diff against the artefact, not a description of it.** Two rounds of "design match" driven by a written punch list each missed most of the real gap; one pass reading the prototype's own computed styles and JS bundle surfaced more than both combined (wrong font, wrong card colour, 3 bands instead of 5, 6 tabs instead of 13, chips where it uses dropdowns). If a reference implementation exists, run it side by side and sample it — never work from a second-hand summary, including one written by another agent or by me earlier in the same session.
- Sample design tokens from `getComputedStyle` on the running reference rather than eyeballing screenshots — screenshots made `#f7f6f4` cards read as white and made STRONG/GOOD (emerald vs sky) look like one colour.
- Be suspicious of confident design rationalisations written into code comments. `lib/types.ts` carried a comment asserting stage pills were "deliberately one flat neutral tone — stage is a workflow position, not a status judgement"; the prototype colour-codes them *and* adds a descriptor line. The comment was an unverified assumption dressed up as a decision, and it then protected the mistake from review.
- **Fidelity to a mockup must never delete real functionality the mockup didn't need.** A static prototype has no auth, so it shows no sign-out control — an agent "matching the prototype" removed ours entirely and left users unable to log out. Before deleting a control because "the reference doesn't have it", ask whether the reference simply had no such concept. Restore it in a way that preserves the visual (e.g. behind an avatar menu).
- **"No dummy data" governs records and figures presented as fact — not a calculator's starting inputs, and not display truncation.** An agent applied the rule literally and (a) zeroed every input in the eligibility calculators *including the lender policy constants* (FOIR factors, multipliers, tenure), making them mathematically incapable of producing any number, and (b) replaced `lead-{id.slice(0,6)}` with the full 36-char UUID. Seed values for a what-if tool and a shortened form of a real id are neither fabricated nor presented as fact.
- When parallelising subagents over one codebase, partition by **file ownership** with an explicit do-not-touch list, and have them read a reference from source rather than share one browser — otherwise they overwrite each other and corrupt each other's session.
- A subagent that dies mid-task (session limit, timeout) can leave a **half-wired feature that still typechecks**: the richer data layer landed in `lib/decision/sections.ts` while `SectionPanel.tsx` still rendered only four of its fifteen block types, so signals/trends/meters were computed and silently dropped. After any interrupted agent run, diff what the data layer *produces* against what the renderer *consumes* — `tsc` will not catch it because unused optional fields are legal.
- Subagents cannot apply Supabase migrations (no MCP access); they can only write the `.sql`. Always check `supabase/migrations/` for unapplied files after an agent run and apply them yourself, or the columns the new UI reads will silently be `undefined`.
- When a mockup shows a metric/ring/badge with no real backing signal in the schema (TAT, a composite "FIT score"), don't fabricate a number — rank/label using whatever *is* genuinely computable (e.g. lowest indicative EMI from `commission_slabs`) and name the label after what it actually measures ("Best fit" from EMI, not an invented score). Applied on the Offers tab auto-ranking (2026-08-22).
- Shared portal components (e.g. `LeadDetail` used by both `/partner/leads/[id]` and `/ops/leads/[id]`) give ops-portal parity "for free" when a feature is built once into the shared component — check whether a route already delegates to a shared component before duplicating a UI fix into both portals.
- A per-partner metric that's meaningless under RLS scoping on the partner Dashboard (e.g. "pass rate by RM" when a partner only ever sees their own leads) can still be genuine and valuable on the ops-wide analytics page, since ops sees every partner — don't reject a mockup metric outright just because it doesn't fit one surface; check whether it fits a different one.
